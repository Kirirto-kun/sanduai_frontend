# Как организованы ветки Sandu AI

Правила одинаковы для самостоятельных репозиториев `sanduai_backend` и `sanduai_frontend`. Корневой локальный репозиторий хранит общие отчёты и не заменяет эти два репозитория.

## Основные ветки

| Ветка | Что в ней находится | Когда обновлять |
| --- | --- | --- |
| `main` | Совместно проверенный код завершённых функций. Здесь могут быть функции, которые ещё не опубликованы на сайте. | После review, разрешения конфликтов и проверок итогового объединённого кода. |
| `production` | Точный Git-коммит, соответствующий фактически опубликованной версии этого компонента. | Только после отдельного ручного релиза и подтверждённой production-приёмки. |
| `codex/<задача>` | Работа над отдельной задачей. | Во время разработки; после интеграции и проверки ветка обычно удаляется. |

Состояние production на 2 ноября 2026 после завершённого Zerde-релиза: backend `2226c33265e8488c4392062cd95b900c2608352d`, frontend `2acb11d14cbd9eced5ca75aeca584023d05b5959`. Дальнейшее движение `main` само по себе эти версии не меняет.

Слияние Training, Science, Zerde, Open Lesson и Preschool в `main` — организация исходного кода. Это не новый production-релиз. Training и Science нельзя объявлять опубликованными по факту merge или наличию локальных тестов.

## Обычный порядок работы

1. Начать отдельную `codex/<задача>` от актуальной `main`. Перед работой прочитать применимый `AGENTS.md` и проверить незакоммиченные файлы.
2. Делать небольшие содержательные коммиты и отправлять ветку на GitHub. Не переносить `.env`, токены, пользовательские данные, дампы, приватные QA-файлы и локальные каталоги сборки.
3. Открыть PR в `main`, описать итоговое поведение и приложить результаты проверок. При изменении общего контракта согласовать оба репозитория.
4. Разрешить конфликты по смыслу и проверить итоговое дерево. Сохранять уже выпущенные исправления, проверки доступа, тарифы, историю и форматы документов. Наличие похожего кода в старой ветке не означает, что нужно вернуть старую реализацию поверх исправленной.
5. Запустить обязательные проверки. Успех старого коммита не считается проверкой нового merge. При изменении итогового дерева повторить затронутые проверки.
6. Слить PR с сохранением понятной истории. При объединении существующих длинных веток сохранить исходные коммиты и их авторство; не переписывать опубликованную историю ради оформления профиля.
7. Убедиться, что GitHub `main` содержит ожидаемый коммит и проверки завершились. Затем удалить только подтверждённо интегрированную и больше не используемую feature-ветку.

## Проверки перед merge

| Компонент | Обязательные проверки |
| --- | --- |
| Frontend | `npm ci`; `npm audit --audit-level=high`; `npm run validate:api-base`; `npm test`; `npm run lint`; `npx tsc --noEmit`; `npm run build`. При изменении Dockerfile/release-конфигурации — сборка image и release preflight. |
| Backend | Установка `requirements.lock` с `--require-hashes`; `pip check`; dependency audit; `ruff check src tests scripts`; compileall; полный pytest. На одноразовой локальной PostgreSQL — одна Alembic head, `upgrade head`, `alembic check` и затронутые PostgreSQL-тесты. При изменении image/release-кода — release-script contracts, сборка image, nonroot и release preflight. |
| Общие сценарии | Маршрут → API → очередь/результат → история → скачивание. Проверить владельца, чужой доступ, сохранение и повторное открытие; для платных операций — idempotency и единственное списание. Новые тесты используют mocks или собственную изолированную тестовую БД; реальный платный вызов требует отдельного основания в задаче. |
| UI и документы | Проверить затронутые экраны на desktop/mobile, RU/KK, клавиатуру, ошибки и скачивание. При изменении renderer/шрифтов визуально открыть реальные DOCX/PDF, а не ограничиваться сигнатурой файла. |

Пропущенные тесты указываются с причиной. Отсутствие PostgreSQL URL или точного лицензируемого шрифта не превращает пропущенный сценарий в успешно проверенный. В CI используются версии Python/Node и команды из `.github/workflows/ci.yml`; их результаты должны относиться к итоговому SHA.

## Удаление веток и сохранность работы

Перед очисткой сохраняются проверенный `git bundle` всех refs и точные снимки незакоммиченных изменений. Файлы другой незавершённой задачи не откатываются и не добавляются в коммит без разбора.

Ветку можно удалить, когда её текущий tip включён в `main`, нет незавершённого PR/работы, а нужные релизные доказательства сохранены. Если изменения перенесены без ancestry, сначала нужно отдельно доказать сохранность всех уникальных коммитов/изменений; одного одинакового имени функции недостаточно. Для исходной консолидации предпочтительно сохранить ancestry.

Не удаляются `main`, `production`, релизные теги, backup bundles, подтверждённые release manifests и данные восстановления. Ветки, занятые активным worktree или другой задачей, сначала проверяются; принудительный reset/remove для «чистоты» не используется. Исторические приватные release-каталоги не считаются мусором только потому, что feature-ветка уже слита.

## Production-релиз

Production меняется отдельной явно разрешённой операцией по release runbook: точные образы и SHA, scope, резервная копия, restore rehearsal, проверенный offsite, применимые миграции, закрытая приёмка, затем открытие и публичная проверка. После успешного релиза `production` указывает на фактически развёрнутый коммит каждого компонента; его соответствие подтверждают release tag/manifest и deployment-отчёт.

Внутри репозитория CI проверяет и собирает образы. Push в `main` не меняет действующий VPS: он работает с отдельно закреплёнными image SHA и ручным release-процессом. Внешние GitHub App/hosting-интеграции проверяются отдельно; наличие исторического deployment само по себе не подтверждает текущую связь с рабочим доменом. Настройка или отключение внешнего deploy-триггера — отдельное изменение конфигурации.

## Авторство и GitHub

Существующее авторство сохраняется. Для текущих коммитов привязка к `Kirirto-kun` подтверждена GitHub API; оснований переписывать авторство нет. Merge в основную ветку и отображение contribution graph — разные проверки. Для приватного backend отображение приватных вкладов дополнительно зависит от настроек профиля GitHub.
